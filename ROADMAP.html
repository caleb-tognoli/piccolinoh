piccolinoh — roadmap

What's next after the Lavalink resolver swap.

Shipped

  • P0 — Server-side audio path removed.
  • P1 — State server + WebSocket protocol.
  • P2 — Web client with synced YouTube player.
  • P3 — Discord bot wired to watchtogether, 9 slash commands, SQLite cache.
  • Lavalink swap — YouTube Data API replaced by local Lavalink resolver.

Phase 4 — Multi-source resolution

User keeps typing into one text field; the resolver figures out where the input came from and always translates it to a YouTube video for the browser player. YouTube stays the sole playback medium — the point is to widen what people can paste in, not to add new playback paths.

  • Spotify URLs. Accept a Spotify track / album / playlist URL in /play. Resolve each track by ytsearch:artist track through Lavalink and enqueue. Needs Spotify Client Credentials (free, no OAuth flow).
  • /thisis <artist>. Fetch the Spotify "This Is <Artist>" playlist, resolve each track to YouTube, enqueue in order. Cache-friendly since the playlist rarely changes.
  • URL-shape dispatch in resolveInput. Small router: YouTube URL / bare id / plain text (existing path) vs. Spotify URL (new path). Text queries stay YouTube-first.
  • Cache scoping. The query_cache key becomes {source, query} so a Spotify URL and a raw text query never collide.

Phase 5 — Discord UX polish

Make the bot feel like a product instead of a CLI. The tentpole is dropping /session — Discord already knows who the user is; the join flow shouldn't need forms.

  • /join replaces /session. Bot replies with a plain Discord link that opens the user's default browser directly. No copy-paste, no join screen.
  • Auto-set display name. The /join URL carries a bot-signed name token (short HMAC over guildId + userId + displayName). Browser skips the name prompt when a valid token is present.
  • Prettier command output. Replace the plain-text replies with a small embed vocabulary — one style for "queued", one for state changes, one for errors. Consistent colors, footers, thumbnails.
  • Minor utility commands. /replay (re-enqueue current), /move <from> <to> (queue reorder — protocol already supports it), /history (recently played), /clear (empty the queue).
  • Autoplay-off toggle. /settings autoplay <on|off> stops scheduleAdvance from promoting the next track.

Phase 6 — Web UI & UX

The web client is functional but bare. Specifics get pinned down when we open this phase; below is the current wishlist.

  • Overall visual polish. Real type scale, spacing, and a considered palette. Presence, queue, transport controls all get a design pass.
  • Now-playing surface. Show title / author / thumbnail / progress bar prominently instead of just leaving the YouTube frame to speak.
  • Queue rendering. Reorderable list with drag-to-move, item-level remove, per-item requester avatar (once names are wired).
  • Mobile polish. iOS autoplay quirks (tap-to-start fallback), touch-sized controls, layout under narrow viewports.
  • Presence display. Show who's actually listening, using the auto-set names from P5.

Phase 7 — Preparing for a real deploy

The install-once-and-leave-it milestone.

  • Session persistence across restart. Serialize Session to SQLite on every mutation, re-hydrate on boot, bump the epoch so browsers resync.
  • WS resync + reconnect backoff. Exponential backoff on the client, drop stale clock offsets, re-fetch state on hello.
  • Control-message rate limiting. Per-client leaky bucket on applyControl in ws.ts.
  • Caddy TLS reverse proxy. Third compose service in front of piccolinoh:3000, Let's Encrypt auto-cert on PUBLIC_BASE_URL.
  • Structured logs + health endpoint. Pino serializers, plus GET /healthz reporting session count and Lavalink reachability.
  • Backup story for piccolinoh.db. Volume snapshotting or an explicit dump-on-shutdown.

Later — worth remembering

Things worth naming so they don't get forgotten, but not slated to a phase yet.

  • User permissions & role model. View-only / controller / DJ split. The control WS message is the single axis to gate.
  • Vote-skip enforcement. skipmode vote already persists; gate /skip on a majority of active listeners once the permission model exists to say who counts.
  • DJ role enforcement. skipmode dj gates mutations on a Discord role. Needs /settings djrole <role>.
  • Full Discord OAuth. Only if the signed-name-token from P5 turns out to be too weak. Otherwise skip.
  • Playlist history & per-guild library. Save enqueued tracks, offer /library lookup, "play something like last Friday" kind of queries.
  • Multi-guild scale. Sharding, Lavalink node pool, DB partitioning — only relevant if the bot ends up in more than a handful of guilds.
